# Bonjour Bangladesh SEO and Analytics Blueprint

Status: implementation specification  
Goal: qualified B2B buyer inquiries, not consumer ecommerce traffic

## SEO positioning

Primary themes:

- garment buying house in Bangladesh
- apparel sourcing company in Bangladesh

Keyword themes below are an intent map, not a fabricated search-volume report. Final priority and paid-campaign grouping should be validated through the client's Google Ads Keyword Planner, Ahrefs or Semrush account.

## URL rules

- Canonical host: `https://bonjourbangladesh.com`
- Redirect `http`, `www` and duplicate slash/case variants to the canonical URL
- Canonical page URLs use a trailing slash; files such as `robots.txt` and sitemap XML do not
- Lowercase English words with hyphens
- No generic URLs such as `/product/product-82/`
- Product URL is independent of taxonomy and freezes on first publish
- Product slug format: `/products/mens-chino-pant-mch-026/`
- Every slug change creates a server-side 301 redirect record
- Sort query keys consistently, normalise permitted values and remove empty/default/duplicate parameters before the canonical response
- Page title and visible H1 are separate CMS fields
- Canonical override is limited to authorised SEO/Super Admin roles

## Faceted navigation

Filters use stable query parameters such as:

`?type=t-shirt&fabric=jersey&season=ss26`

Rules:

- Filter, sort, page-size and internal-search combinations: `noindex,follow`
- Canonical filtered views to the nearest clean category landing page
- Exclude filter parameters from all sitemaps
- Use accessible form controls rather than generating thousands of crawlable filter links
- Equivalent, duplicate and out-of-order parameters normalise to one URL using redirect/canonical rules
- Valid zero-result filters return a useful `200 noindex,follow` state with filter removal; malformed or unsupported paths/values return a real 404
- Internal search results remain `noindex`
- Pagination uses crawlable links and self-canonical page URLs; do not canonical every page to page one
- Do not initially block filter URLs in robots.txt because crawlers need access to read `noindex`
- Review Search Console and server crawl logs before later parameter blocking

Google warns that uncontrolled filters create near-infinite URL spaces and slow discovery of useful pages. See [faceted-navigation guidance](https://developers.google.com/crawling/docs/faceted-navigation).

## Product-page SEO requirements

Server-render in the initial HTML:

- Product name and style code
- Audience, construction and product type
- Fabric/composition, GSM, fit, sizes, colours and season
- Features, finish/wash and description
- Gallery image elements and ALT text
- Breadcrumbs and parent-category links
- Related products
- Product-prefilled RFQ link/button

MOQ, lead time, capacity, pricing and certification appear only when verified.

Publish-time validation requires a unique slug, product title and style code; a cover image and useful ALT text; sufficient original visible specifications/description; and an indexability decision. Incomplete preview records stay draft or `noindex`. Duplicate title/meta/description checks warn the Product Manager and SEO Editor before publication.

Product lifecycle:

- Temporarily unavailable but useful product: keep `200`, explain inquiry availability and show alternatives
- Permanently retired product with a clear replacement: `301` to the closest genuine successor
- Permanently retired with backlinks/demand but no replacement: retain an informative `200` archive with alternatives where honest
- Legally or intentionally removed with no useful substitute: `410`
- Never redirect every retired product to the products index

Product images require:

- Descriptive filenames
- Specific, concise ALT text
- Width and height attributes
- Responsive `srcset`
- AVIF/WebP with JPEG fallback where supported
- Lazy loading below the first viewport
- Original/large zoom asset loaded only after interaction
- Image entries in the product sitemap

Google recommends standard HTML image elements and supports image sitemaps. See [Google image SEO guidance](https://developers.google.com/search/docs/appearance/google-images).

## Technical SEO

- Next.js SSR/ISR for public pages; do not rely on browser-only rendering for primary content
- Laravel publish events trigger HMAC-protected Next cache/tag revalidation
- Standard crawlable `<a href>` navigation
- One self-canonical per clean indexable page
- One H1 and logical heading structure
- `lang="en"`; no `hreflang` until another language exists
- Correct 200, 301, 404 and 410 responses; no soft 404 pages
- No session IDs, PII or tracking values in canonical URLs
- Unique titles, descriptions, OG image and social metadata
- Automated redirects on slug change
- Staging protected by password, `noindex` and robots disallow
- Preview and admin/API routes never indexable

### Sitemap index

- `/sitemap.xml`
- `/sitemap-pages.xml`
- `/sitemap-categories.xml`
- `/sitemap-products.xml`
- `/sitemap-insights.xml`

Only canonical, published URLs belong in sitemaps. `lastmod` reflects actual content changes, not every deployment. Google explains sitemap discovery and media support in its [sitemap documentation](https://developers.google.com/search/docs/crawling-indexing/sitemaps/overview).

### Robots rules

Allow public pages and product media. Disallow:

- admin and login
- private API routes
- preview URLs
- internal search

Declare the production sitemap index.

Private tech packs are protected by authentication/authorisation and time-limited signed URLs, and return `X-Robots-Tag: noindex`. A robots.txt disallow is only defence-in-depth and must not reveal predictable private paths.

## Structured-data map

| Page | JSON-LD types |
|---|---|
| Home | `Organization`, `WebSite`, `WebPage` |
| About | `AboutPage`, `Organization`, `Person` for the verified MD profile |
| Inner pages | Correct `WebPage` subtype plus `BreadcrumbList` |
| Contact | `ContactPage` and Organization contact data |
| Capabilities | Semantic `Service` entries with Organization provider |
| Product | `Product` using only visible, verified data |
| Insight | `Article` or `BlogPosting` with real author/reviewer and dates |
| FAQ | Optional `FAQPage` matching visible questions and answers exactly |

Never add fake offers, prices, availability, ratings or reviews. Google Product rich-result eligibility requires a genuine offer, review or aggregate rating; this inquiry-only catalog must not promise rich Product results. See [Google Product requirements](https://developers.google.com/search/docs/appearance/structured-data/product-snippet).

Use stable fragment identifiers such as `/#organization`, `/products/example/#product` and `/#breadcrumb`. Map style code to `sku`. Use one `Product` when colours/sizes are selectable specifications of the same inquiry item; use `ProductGroup` with visible `hasVariant` products only when variants have distinct public URLs or materially distinct specifications. Do not manufacture variants for schema alone.

FAQ markup may support machine understanding but is not presented as a guaranteed rich-result strategy.

## Internal linking

- Home links to primary categories, capabilities, quality, compliance, sustainability and RFQ
- Products link audience → construction → all products through normal HTML links
- Product detail links to parent categories, three to six related products, one relevant capability/article and prefilled RFQ
- Capability pages link to supporting quality/compliance/sustainability pages and product examples
- FAQ answers link to deeper pages only where genuinely useful
- Insight articles link to a relevant commercial page; category pages link back to one to three strong guides
- Breadcrumbs appear on all products, articles and inner pages
- Footer exposes all trust and legal pages
- Run a quarterly orphan-page crawl

Google uses crawlable link relationships to understand site hierarchy. See [Google site-structure guidance](https://developers.google.com/search/docs/specialty/ecommerce/help-google-understand-your-ecommerce-site-structure).

### Events

GA4 recommended events:

- `view_item_list`
- `select_item`
- `view_item`
- `search`
- `generate_lead`

Custom product and conversion events:

- `product_filter`
- `rfq_start`
- `tech_pack_upload`
- `whatsapp_click`
- `email_click`
- `phone_click`
- `meeting_request`
- `ai_invite_shown`
- `ai_chat_open`
- `ai_message_sent`
- `ai_lead_handoff`
- `inquiry_popup_view`
- `inquiry_popup_dismiss`

CRM lifecycle events sent server-side where configured:

- `working_lead`
- `qualify_lead`
- `disqualify_lead`
- `close_convert_lead`
- `close_unconvert_lead`

Only completed `generate_lead` is the primary key event. Clicks, chat opens and form starts are micro-conversions.

Event contract minimums:

- Ecommerce-style events include `items[]`, stable `item_id` = style code, item name, audience, construction and product type
- Search includes `search_term`; filter includes selected key/value pairs and result count
- CTA/form events include `source_component`, source page and product/style context where applicable
- `tech_pack_upload` fires only after a successful accepted upload, never on selection or failure
- `generate_lead` fires once from the server-confirmed success state and uses an opaque lead/event ID for deduplication
- Meeting request is a parameter on a successful lead plus the `meeting_request` micro-event; no date, agenda or contact PII enters analytics

Capture in Laravel:

- First and last UTM values
- Landing page and referrer
- Product/style context
- Source component
- Supported ad click IDs

Never send names, email, phone, message, filename or tech-pack content to analytics. Use an opaque lead ID and deduplicate client/server events. See [Google Analytics PII policy](https://support.google.com/analytics/answer/6366371).

Tracking hygiene:

- Staging, preview and local environments never send production analytics
- Exclude known staff/internal traffic and mark QA/test submissions
- Do not count bots, spam, validation failures, blocked uploads or mail failures as conversions
- Keep raw UTM/ad-click values in the lead record only when permitted by consent; analytics receives normalised non-PII campaign fields

Consent for UK/EU visitors:

- Consent Mode v2 defaults advertising and analytics storage to denied until a valid choice where required
- Non-essential analytics, advertising and Clarity tags remain blocked until the matching consent
- Essential inquiry storage, security and user-requested contact remain available and are documented separately
- Consent version, region logic and timestamp are auditable; withdrawing consent updates tags and future storage
- Clarity is optional and launches only after privacy review, masking configuration and matching consent

## Performance and accessibility targets

At the 75th percentile for mobile and desktop:

- LCP at or below 2.5 seconds
- INP at or below 200 milliseconds
- CLS at or below 0.1

These are the current Core Web Vitals thresholds. See [web.dev Web Vitals](https://web.dev/articles/vitals).

Additional gates:

- Responsive checks at 375, 768, 1024 and 1440px
- Keyboard navigation and visible focus
- WCAG AA contrast
- Accessible filter drawer and gallery/lightbox
- No autoplay audio before user interaction
- Timed inquiry prompt is frequency-capped, suppressed after conversion or active form/chat use, dismissible for seven days and non-intrusive on mobile
- Reserved media dimensions
- Minimal critical font preload
- No zoom image in initial payload
